Low-and-slow probing that never gets an answer

"Device identification attack" is pure Modbus (fc43, Report Device Identification) — fully visible to the pipeline, unlike address scan. But it isn't one burst either: it repeats as 16 tiny rounds (8 rows, ~1.9 ms each, one new TCP connection per round) spread across almost the whole session, roughly once every 5.8 minutes. And every single probe gets the same answer: an identification reply with zero objects in it — unlike the function-code scan's fc17 probe, which leaked a real string.

A probe that reaches the device but learns nothing

Compare this to the function-code scan's fc17 (Report Slave ID) probe, which decoded to the string "Pymodbus". This device's fc43 handler is well-formed but empty.

fc43 itself is not inherently malicious

Worth being precise about what "0 in normal traffic" does and doesn't prove, beyond this one simulated session.

Read Device Identification (fc43/MEI 14) is a standard, documented Modbus feature (Application Protocol spec v1.1b3), legitimately used by real asset-management tools and engineering workstations for maintenance inventory - and, per published ICS security research, the exact same request is also a known reconnaissance technique when swept across a network (Radiflow, "Hack the Modbus"). "0 occurrences in normal traffic" is true for this dataset's definition of normal (continuous SCADA measurement polling only, no asset-audit traffic modeled) - it is not a universal claim that fc43 is always an attack. What actually distinguishes this case is the requester's identity (never a known engineering host) and the repeat cadence (16 systematic, evenly-paced rounds probing all 3 access codes) - a pattern that reads as automated tooling, not a one-off manual maintenance check. Detection logic built from this page should key on identity + cadence, not on fc43's mere presence.
